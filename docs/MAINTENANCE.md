# Maintaining Quiznet

The owner controls releases and repository visibility. Change visibility only with explicit owner authorization, and keep the repository name and URL unchanged unless a change is requested.

Release names and stages are defined in [RELEASES.md](RELEASES.md); feature plans are in [ROADMAP.md](ROADMAP.md). Run `npm run release:info` for the current public name and technical installer version. Release planning belongs in the repository and release notes; Settings shows only the technical version for diagnostics.

## Storage and compatibility

The first-run seed now creates exactly one collection, course, unit and ten-question showcase quiz. `src/showcase.json` is bundled; `src/sample.cjs` assigns the collection and course appearance. `Store.load` invokes it only when both the primary library and rolling backup are absent. Never inject this seed into an existing or deliberately emptied profile, replace a recoverable backup with it, or use it to reset study data. Legacy choice-only test material is an explicit test fixture, separate from the current first-run experience.

`written-answer` and `matching` extend the shared question model without changing library schema version 1 or choice-question contracts. Written questions store 1–20 `acceptedAnswers` strings (at most 2,000 characters), plus validated `caseSensitive`; responses are bounded strings. Grading uses NFKC, trimmed/collapsed whitespace and optional case folding, with no fuzzy or AI grading. Matching stores 2–20 plain `{left,right}` pairs (1,000 characters per side); responses map each left item to a distinct original right index, with explicit nulls for unfinished connections. Partial strings/maps travel with resumable sessions and are distinguished from complete checked answers. Matching right order is a deterministic seeded derangement, stable across rerenders/restarts and separate from the original answer key. Both new types require explicit instant-feedback checks; only single choice/true-false auto-check on selection. Preserve pending-response flushes before navigation and close.

Pending responses save through the existing validated change endpoint. Navigation locks response fields while an action is pending; typed input retains focus during ordinary autosaves. During the close handshake, only answer, daily-answer, saved-answer and mistake-answer mutations may drain while other changes stay blocked. A failed save keeps the window open for retry and preserves the last committed files.

Shared validators, scoring, recovery drafts, saved/daily/mistake workflows, fingerprints, report/copy generation and AI brief schemas handle each type. Keep accepted alternatives and correct matching connections out of copied questions or unrevealed previews. Completed study reports intentionally include them. Existing choice fingerprints remain unchanged, so old saved stars and review identities stay linked. Old choices/history retain their original shapes and active answer order. Backups keep the same format and include new response fields. Older app versions do not understand the new types and can reject a library containing them; retain a full backup and a compatible installer before rollback.

Interface languages add a validated `language` field to version-1 `display.json`; old files default to English without a rewrite. Unsupported saved languages preserve the original preference file and other display choices. A missing bundled language script falls back to English without touching the library or recovery draft. Registry metadata, offline catalogs, formatting and direction are shared through `languages.js` and `i18n.js`; `localization.cjs` translates native dialog labels without changing file paths or behavior. Catalogs use fixed local paths and do not expand IPC or network access. Study content, custom names, schema IDs, exports and generated instruction text stay unchanged. See [LANGUAGES.md](LANGUAGES.md) for catalog validation, plain-text/trusted-fragment boundaries, RTL and contributor workflow.

The interface cleanup changes presentation and action placement only. Library **+** owns creation; **⋯** owns course/collection organization. Course commands stay in Course actions/contextual menus, with a compact assigned-focus summary. Settings/Explore omit creation, Settings uses its own search, and Ctrl+K remains global. Help owns offline reference and issue reporting; About ends the Settings navigation and owns version/license/privacy/project/update information. `app-information.js` contains the repository MIT notice; keep it synchronized with `LICENSE` when that notice changes. Shared modal paragraph/heading rules target direct dialog text, and start controls have an explicit surface class so page/preview styles do not affect them. Existing IPC, defaults and study state are unchanged.

The Settings workspace extends version-1 `display.json` additively: theme, accent, reading-text scale, density, study defaults, History filter/tab/group choices and recovery limits. Legacy files acquire defaults on read without being rewritten. The main process validates enum choices, bounded scales, study options, filter shape and recovery budgets; writes remain serialized and atomic. Renderer controls wait for a pending preference save, avoiding dropped changes. Light-theme surfaces and local default-icon colors use theme roles; explicitly chosen course colors remain user-owned. Follow Windows uses the local color-scheme media query.

Quiz appearance adds an optional nested `quizAppearance` object to the same version-1 device preferences. Its shared plain-JavaScript validator supplies defaults for old/partial files and accepts only shipped enum choices, size catalogs, booleans and empty/six-digit hex colors; unknown keys and arbitrary CSS/URLs are rejected. The renderer produces a fixed set of CSS variables/attributes, uses local font stacks, and keeps quiz, marker and editor resets independent. Code wrapping changes presentation only. Live previews have no editor-data bindings and never create recovery drafts. Preference changes preserve unfinished answers, source text, history and library bytes. Default values retain the established layouts and sizes. No library migration, new IPC capability, dependency or network access is introduced.

The unified Appearance workspace groups App, Quiz, Review and Editor beneath one Settings destination. Review overrides extend the existing `quizAppearance` object additively; defaults preserve the previous inherited reading style. The main process uses the same bounded validator and atomic preference setter. `quizSurface`, `dailyReviewSurface` and `reviewCard` render both study screens and previews; editor previews reuse `editorQuestion`. Only fixed synthetic questions enter these samples. Before insertion, preview controls receive local-only action names, IDs/references are namespaced, editor bindings are removed and made read-only/disabled, and copy/menu/exit controls are disabled. Preview state remains renderer-only and never invokes a study mutation, clipboard operation or draft save. The full-window preview uses the existing accessible modal. CSS names are scoped to avoid course-customization collisions. No external reference code, package or online theme service is bundled.

Answer-choice shuffling adds optional `shuffleAnswers` practice metadata and a validated `optionOrders` permutation for every question in an unfinished ordinary attempt. Stored answers and grading use canonical indices; the UI and number shortcuts map the visible permutation to those indices. Resume and backup/restore preserve the permutation. Finished results keep canonical question/answer snapshots. Copy question orders its choices as shown, without exposing the answer key. No library-version change is needed.

History management resolves selected IDs against main-owned completed attempts, bounds selections at 10,000 unique entries, and rejects unknown IDs or a result required by active missed-question practice. Preview tokens are main-owned; confirmation revalidates before the serialized delete transaction takes a recovery snapshot. Failures preserve committed state. CSV exports contain session summaries, quote fields and neutralize formula-leading names; native save dialogs control paths. No history removal runs during installation or smoke checks against the real profile. Storage summaries inspect only known study/preference files and recognized recovery points. Configured retention prunes recognized old recovery files only after a new point is saved, keeping that new point regardless of budget. Repository and issue opening accepts only two fixed page keys; all renderer network/navigation restrictions remain in place.

Display preferences are version-1 `display.json` in the existing user-data directory, outside the study library. The main process validates the three library views, remembered-view boolean, and 90/100/115/125 percent interface scale; these and the additional Settings choices described above cross the validated IPC setter. Writes are serialized and atomic, keep the old state on failure, and preserve a damaged preference file before replacing it. Startup reads without creating or rewriting the library. Disabling remembered views persists Cards for next launch while allowing a renderer-session layout choice. Scale uses Electron's bounded zoom factor, including after renderer recovery. Shutdown waits for pending preference writes. Library filtering, layout changes and resizing do not mutate questions, history or unfinished sessions. Narrow Details tables scroll inside their own region; collection tabs scroll without widening the app.

Library organization adds optional root `collections` (at most 1,000), course `collectionId`, and course/collection `appearance` and `pinned` fields to version-1 libraries. Collections reference courses without nesting or moving their study objects. Collection IDs participate in global ID uniqueness and all course references are validated. Appearance accepts only a shipped icon ID or bounded plain symbol plus empty/default or six-digit hex colors; renderer SVG comes only from the local catalog. Global course array order and collection array order are stable; pinning is a presentation partition. Up/down moves swap eligible peers (all pinned courses, or unpinned courses in the same collection; collections within their pin state). Collection removal clears references, preserving courses and taking the standard delete recovery snapshot. All mutations use existing serialized/atomic store transactions. Old libraries omit these fields and remain unchanged on read; rollback to old builds can discard optional organization metadata.

History uses an optional course `studyFocus` enum (`long-term`, `for-now`, `low`, `unset`); the course-focus action removes the field when reset to Not set. Old courses without it load unchanged. Main-process validation rejects unsupported values, and the existing serialized transactions/backups retain the field. History analytics are read-only renderer computations over completed attempts and the current course/unit/quiz hierarchy. Current course focus applies to earlier attempts; quiz moves likewise use current locations. Unlinked legacy attempts remain visible. Metrics count repeated answers explicitly, sum only known active/partial timing, and separate missed-only sessions from latest/best full-quiz scores. Daily/saved/notebook rounds are outside ordinary attempt history. No new IPC, network capability, library version, or dependency is added. See [feature batching](FEATURE_BATCH.md) for the current workflow and status.

Saved-question entries may include an optional `origin` containing main-owned course/unit/quiz IDs and titles. New stars capture it when the source is identifiable; validation retains it through backup/restore within the existing 64 MiB state bound. Existing entries without origins load unchanged. Filtering resolves stored origins against current quiz locations, then supplements them with exact-content matches from live quizzes and historical attempt snapshots. Deleted origins use their captured path; unresolved legacy copies stay accessible as unlinked. The main-owned page endpoint validates cascading filters, filters before its 20-item pagination, and returns scoped choices/counts. Starting saved practice resolves the same filter in the main process and freezes only matching keys; resuming never replaces an active round. Filter browsing and inference are read-only, and filter preferences remain renderer-session state.

Saved questions use an optional version-1 `savedQuestions` field in the existing version-1 library, with at most 20,000 immutable question copies / 64 MiB, one practice session of at most 100 keys, and one last-round summary. The shared canonical content signature excludes question IDs; the main process stores a SHA256 key and an independent snapshot ID. Source selectors resolve against saved main-owned quiz/attempt/daily/notebook state rather than accepting renderer-provided question bodies. Main-owned pagination returns 20 entries. Saved answers/checks serialize with the library, advance using rotating tokens, and require exact correctness. Source edits/deletes never reconcile away saved copies. Unsave is idempotent, snapshots first, and rejects active round members until finish/discard. A failed write keeps both prior files and in-memory state intact. Old libraries without the field load unchanged. `copyQuestion` and `instructions(copy)` await Electron's asynchronous clipboard write; renderer networking and permission denials remain in place. No dependency or profile is added.

Copy question uses renderer-side source formatting and a narrow `copyQuestion` IPC method. The trusted main process validates a nonempty string up to 20 MiB before writing plain text to the clipboard. No store mutations, arbitrary URLs, HTML clipboard insertion, external navigation, or network requests are involved. Result buttons select the original historical array index (including across filtered/paged reviews). The formatter only receives the chosen question and emits prompt/choices/code; it never appends correctness fields, explanations, selected answers, or notes. Existing inert HTML rendering supplies text extraction; Markdown/math remains source, with embedded images replaced by descriptions. No storage field or dependency is added.

Home derives its read-only cards from existing quiz sessions, daily-review state, focused mistake sessions, editor-draft metadata, and historical attempts. It adds no stored fields or IPC endpoints. The existing internal `home` action continues to open Library for established breadcrumbs and result navigation; `dashboard` opens the Home page and brand target. Startup uses the Home view. Existing workflow tests explicitly enter Library, while Home tests cover default startup, empty data, resume and timing pause, recent-result deduplication, cancelled quick actions, local-day refresh, escaping, and minimum-window layout.

The shared header exposes one icon-only Search library action with an accessible name and Ctrl+K shortcut. In the Library overview, the + menu offers New quiz, New course and New collection; study/browsing pages retain New quiz; Settings and the Explore placeholder omit it. The quiz chooser groups manual editing, agent preparation, and file import. It is hidden during study and brief preparation. Settings appears in the sidebar, with a header fallback only when navigation is hidden; Help actions live inside Settings → Help. About is last and holds app/license/privacy/project information and updates. Library actions / Course actions / Unit actions hold local organization commands. Quiz discard stays with the active quiz/resume surface. Home has no duplicate creation shortcuts. Breadcrumbs identify saved practice, notebook practice, daily review, and historical results. Search is read-only and includes empty units, course names, quiz titles, and question text; it bounds displayed results at 50 per type and escapes titles. It uses existing navigation, start-options, modal focus, and Ctrl+K handling, with no storage or IPC changes. Header tests cover search destinations and empty states, escaped unit names, focus restoration, cancelled actions, current creation/brief destinations, long titles, compact windows, and hidden navigation.

The optional version-1 `mistakeNotebook` library field holds daily-review mistake snapshots, notes, pinned historical questions, and a focused practice session. Historical quiz mistakes are derived read-only from saved attempts, grouped by SHA256 of normalized question content excluding IDs; a content change gets a separate note identity. Pins have zero additional daily occurrences so historical counts are not duplicated. The main-owned notebook endpoint pages 20 entries; focused sessions pin at most 20 snapshots, validate answer sets, lock checks, and rotate tokens on advancement. Session progress and notes use ordinary serialized library transactions, backups, recovery, and restore. A failed snapshot/note write rolls back the complete change. Saved entries are bounded at 20,000 / 64 MiB with explicit errors; note length is 5,000 characters. Old libraries without this field load unchanged. No dependencies are added.

Daily review uses an optional version-1 `dailyReview` field in the existing version-1 library. It is validated on load/restore and saved through the same serialized, flushed library transactions and snapshots. Existing libraries without it load unchanged. State contains the daily limit, selected quiz IDs, up to 100,000 question schedules, at most 366 local-date count records, and one active question/answer/check token. The main process computes eligibility and intervals, enforces the cap, locks checked answers, and rejects duplicate/stale rating tokens. Ratings do not create or modify ordinary attempts. Identical question content is matched one-to-one when the editor regenerates IDs; changed/deleted questions are pruned. No dependencies or separate profile are added. Tests cover backup round trips, failed saves, concurrent ratings, day rollover, and real desktop resume/restore. Older app builds can discard the optional field; retain a backup before rolling back.

Study reports use the completed attempt snapshot and shared correctness rules, independently of the current quiz, result filter, or visible page. The main process accepts only a saved attempt ID and a validated all/focus scope. It bounds the report at 20 MiB and 10,000 questions, quotes source with collision-safe fences, deduplicates valid embedded raster images, and keeps null/partial/legacy timing explicit. No library field is added or changed. Report exports use a native Markdown save dialog, reject the app data folder, serialize concurrent exports, and flush a uniquely named temporary file before atomic replacement. Cancellation or failure preserves existing reports and study files; graceful shutdown waits for an active report export.

The installer version in `package.json` is separate from the stored library's `version`. The current library schema is version 1. An app-version increase does not require a schema change. Consult [CHANGELOG.md](../CHANGELOG.md) for the development history; this guide describes the current contracts.

See [LIMITS.md](LIMITS.md) for tested workloads and hard versus practical limits. `npm test` includes the storage fault and boundary tests in `tests/stability.test.cjs`; Electron stability checks exercise close-time write failure, renderer recovery, failed checkpoints, and the real 10,000-question workflow. Temporary primary and backup files require disk headroom; do not replace the atomic backup step with an in-place overwrite.

- Keep `com.quiznet.desktop`, product name `Quiznet`, installer name `Quiznet-Setup.exe`, and the Desktop shortcut stable. Study data lives in `%APPDATA%\Quiznet\data`, outside the installation; updates and uninstalls preserve it.
- `src/store.cjs` serializes mutations and saves with flushed temporary files and atomic replacement. `library.json.bak` holds the previous successful state. Restores preserve a separate pre-restore copy; damaged files remain available for recovery. Unsupported or damaged data must produce a recoverable error, never a silent reset.
- Question types and scoring are shared between core and UI. Multiple answers require the exact correct set, with no partial credit. Historical attempts retain their own question snapshots, including media, formatting, and code.
- Practice settings, saved presets, flags, and unfinished attempts travel with backups. Starting an attempt copies its settings, so later preset changes cannot alter it. Instant-feedback checks lock answers in the main process as well as the UI; pending saves must preserve those locks and restore usable controls after failure.
- Missed-question practice uses the original attempt's saved questions through `sourceAttemptId`, leaving that result and the live quiz unchanged. Validation requires exactly the incorrect subset. Deleting the live quiz uses the established path that removes its history and active session.
- The main process owns timing and serialized writes. Answers, navigation, pause, finish, 15-second checkpoints, and graceful shutdown settle the active clock. Startup and restored backups begin paused; downtime is excluded. Partial timings must remain distinguishable from fully tracked attempts. Comparisons require compatible question sets, feedback modes, and full/missed-only scope.
- Images are embedded raster data, never external filenames or URLs. Limits are 2 MB per image, 19 MB per edited quiz, and 20 MB per quiz import. Whole-library backup restore is separate from quiz import and does not use that file-size limit.
- Code attachments allow 50,000 characters; Markdown fields allow 100,000. Highlighting stops above 12,000 characters per block. Unknown languages remain readable as plain code. Content passes through the shared formatting allowlist; imported attributes cannot become app controls. Snippets are never executed.
- The instruction builder generates text from validated preferences and shared catalogs. It never uploads material or reads library content to create the instructions. Generation preferences guide an external agent; they are not additional stored question fields.
- Editor recovery uses a separate version-1 `editor-draft.json`, limited to 20 MiB. It accepts incomplete questions but validates types, choices, answer indices, field bounds, and raster media. Writes are serialized and atomic; the renderer acknowledges successful persistence. A close handshake flushes pending editor changes, and failures keep the app open. The library schema remains version 1. Closing a dialog keeps its edited draft; Cancel discards it; saving the quiz clears it. Agent instruction preferences remain in memory.
- `snapshots/` retains up to 7 recognized recovery files within 128 MiB, keeping the newest file even if it alone exceeds that budget. Save the previous library before the first mutation each UTC day and before import, delete, and restore. Invalid mutations do not create snapshots. A snapshot failure prevents that mutation; a later retry is allowed. Retention deletes only recognized snapshot filenames after the new file is committed. Exported backups and legacy `before-restore-*` files are not pruned. Startup, listing, and Check library do not rewrite the library or rolling backup. Snapshot restore validates content and safe file identity before presenting confirmation.
- The main process validates course/unit ownership and names and creates destinations in the same transaction as the quiz. Matching names reuse existing courses/units. Moving transfers the existing quiz with its IDs intact, preserving history and unfinished progress; it never deletes an empty source parent.
- Import reports compare normalized question content without IDs (answer-set order is ignored), report repetitions and missing explanations, and optionally compare counts/types with a valid in-memory agent brief. Question preview adds bounded per-question issue lists, conflicting-key checks for matching stems/options/attachments, conservative local quality heuristics, and related-question references. Only two distinct answer-key representatives per stem are needed to avoid pairwise scans. Warnings do not remove content, merge quizzes, or claim factual validation.
- The pending import remains in the main process. Initial metadata includes counts and flagged question indices, not every question body or attachment. `importQuestion` requires the current token and valid integer quiz/question indices and returns one copied question and its notes. The renderer reconstructs content through the existing safe content renderer and checks visible text for the displayed question. Correct-answer styling, labels, explanations, and answer-revealing review details require the explicit reveal button. This renderer-only state starts hidden and resets before loading any question. Closing or replacing the import dialog expires its token. Browsing/filtering never calls a library mutation; final confirmation imports the full original batch transactionally. Keep only one question card in the DOM, including for 10,000-question imports.

The pinned development packages `markdown-it`, `@highlightjs/cdn-assets`, and `katex` supply committed browser assets, local math fonts, and licenses in `src/ui/vendor`. Math uses the existing Markdown strings and embedded raster images; library schema and question storage do not change. Only generated KaTeX output bypasses ordinary formatting reconstruction; imported HTML retains the existing allowlist. Keep trust disabled, macros fresh per formula, bounded formula counts/source/expansions/sizes/output/cache, escaped fallback text, and fonts bundled locally. Text/HTML and code blocks must retain literal math-like content. `content.plain` replaces generated math with its source once for search and review checks. Add supported languages through `code-policy.js`, regenerate with `npm run assets:content`, and verify with `npm run check`. Re-audit package changes. The app must not resolve runtime packages or fetch CDN resources.

Older app builds may discard optional fields or fail to resume newer practice sessions even when the library schema number matches. Preserve a full backup before any rollback and verify compatibility with the target build.

For a future schema change, define and test a migration from every supported older schema. Preserve the original file before migrating. A migration must be repeatable without duplicating material and must preserve history and saved attempts. Never test destructive operations against a real study library.

## Review and dependency updates

Use small pull requests and the contribution guide. Read dependency release notes and inspect lockfile changes, especially Electron and installer updates. Dependabot proposes monthly npm and GitHub Actions updates; maintainer approval and passing checks are required before merging.

CI actions are pinned to full commit hashes. The Gitleaks binary is pinned to an official release and SHA256 checksum in `.github/scripts/check-secrets.ps1`. When updating it, download the official checksum file, verify the Windows x64 archive, and update the version and expected hash together.

Keep GitHub token permissions at read access for builds and disable persisted checkout credentials. Do not use `pull_request_target` to execute contributed application code with elevated permissions.

## Build and verify an update

1. Increase the app version with `npm version <version> --no-git-tag-version`; public names use that version, such as `Quiznet v1.37.0`. Advance the internal `quiznetRelease` counter and keep its stage unless the owner explicitly approved changing it. Run `npm run release:info` and update `CHANGELOG.md` using the public name and stage, changes, checks, limitations, and next goals. Keep the app ID, product name, data path, installer name, and shortcut name unchanged.
2. Run syntax, core, Electron, dependency, and secret checks from `CONTRIBUTING.md`.
3. Build on Windows:

   ```powershell
   $env:CSC_IDENTITY_AUTO_DISCOVERY = 'false'
   npm run build
   ```

4. Back up the existing library before testing an update. Record the SHA256 of `library.json` and its rolling backup while the app is closed.
5. Install `dist/Quiznet-Setup.exe`, then run that installer again. Confirm one installed application, the same install directory, and one Desktop shortcut targeting the installed `Quiznet.exe`.
6. Verify both recorded data hashes are unchanged by installation. Open the app, confirm its version and data path, and check that opening it again restores the same window. Perform destructive test operations only in disposable test data.
7. On disposable older-version data, verify upgrade compatibility and any migration. Keep a last-known-good installer privately for rollback. Do not assume an older app can read a newer schema.
8. Generate an installer checksum:

   ```powershell
   Get-FileHash -LiteralPath dist/Quiznet-Setup.exe -Algorithm SHA256
   ```

   Match the checksum to the exact file that will be distributed.

The build creates an offline installer and does not publish automatically. `--publish never` is deliberate. The current Windows installer is unsigned; document signing status accurately.

## Distribute a release

The Windows workflow uploads `Quiznet-Windows`, containing `Quiznet-Setup.exe`. Artifact downloads require GitHub sign-in and read access, and artifacts can expire. [GitHub artifact documentation](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts).

After the owner approves publication, tag the tested commit with `v<app version>` and create a GitHub Release titled with the public name from `npm run release:info`, such as `Quiznet v1.37.0`. Internal `alpha` and `beta` stages remain prereleases; marking a release stable requires owner approval. Include the installer, its SHA256 checksum, and notes from the changelog. Verify the downloaded release asset against the checksum. Maintain one installer filename; releases do not create separate installed programs. Publishing or completing features never changes the stage automatically.

Updates use the same installer filename and existing installation. Keep study backups and local test artifacts outside tracked source. The optional main-process release checker queries only the fixed public GitHub source and never changes study files. Settings offers a manual check and opt-in 48-hour checks. It opens a verified release page after an explicit click; installation still uses the same offline NSIS installer. Device preferences live in `updates.json` outside the library. Keep renderer requests/navigation blocked and never accept a renderer-supplied source URL or credential. See [update checking](UPDATE_CHECKING.md) for bounds, retry behavior, and the separate future installer-verification work.

## Distribution checks

- Confirm publication is approved. Keep the repository name, URL, and visibility unchanged unless a change is explicitly requested.
- Check source, examples, screenshots, release assets, artifacts, and Actions logs for private data. Run the redacted history scan and dependency audit; keep study libraries, exports, credentials, and local audit records out of Git.
- Use the public GitHub handle and a GitHub noreply email for maintainer commits.
- Verify the license, contributor instructions, README download link, release name, and installer checksum match the tested release.
- Keep branch protection, secret scanning, and private vulnerability reporting configured where available. Owner-authorized maintainer updates go directly to `main` after the required checks; external contributions use review.


Quiz references use an optional `reference` object with `title`, Markdown `content`, `scope` (`all`/`selected`) and zero-based `questions` indices for selected scope. Question `hint` is optional Markdown. The shared study-aids validator bounds every field. Attempts snapshot one sheet and remap indices to their own question order; detached saved/mistake questions use a validated `studyReference` context snapshot excluded from their content identity. Old data without these fields stays unchanged. UI access is read-only and uses the existing safe content renderer and icon system.

Written self-review is optional grading metadata, not a question-content change. `selfCorrectedIndices` stores validated zero-based positions in active ordinary attempts and completed snapshots; `selfCorrected` is a validated boolean on checked Daily/Saved/Mistake current-question sessions. Only complete written responses can be corrected. Automatic matching remains deterministic. Scores, missed subsets, notebook collection and reports use the shared reviewed-correctness helpers. Marking a completed result is blocked while missed practice depends on it. The original response and historical answer key remain intact. Adding an accepted response is an explicit separate choice, bounded and deduplicated, and only updates one identifiable unchanged original question in the same atomic library transaction. It preserves question IDs and daily schedules; independent saved snapshots keep their original identities. Failed persistence rolls both changes back. No migration, dependency, network access or IPC endpoint is added.
